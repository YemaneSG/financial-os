## 3. Independent understanding

**The user problem:**

Yemane spends money continuously but has only merchant-level transaction records from bank feeds, which obscure the item-level purchasing decisions behind every dollar. This prevents meaningful understanding of spending habits, price trends, and priority alignment. The problem is particularly acute for large mixed-basket purchases such as grocery and warehouse runs. Bank feeds also arrive without the personal context needed to separate personal spending from charges that occasionally relate to a rental property.

**The proposed outcome:**

A private, single-user production system where the owner can install a PWA on an iPhone, photograph a receipt within ten seconds, receive a truthful server-confirmed acknowledgement, and later retrieve a validated structured extraction of the merchant, date, totals, and individual line items — or an explicit review or failure state that preserves the original evidence. This provides an item-level dataset as the foundation for later analysis, conversational querying, and a local language model, none of which exist yet.

**The smallest release:**

Sprint 0 and 1: project scaffold and CI/CD pipeline, then one end-to-end vertical slice — iPhone PWA camera capture, authenticated direct upload to private object storage, durable PostgreSQL receipt record, asynchronous Vertex AI Gemini extraction, deterministic arithmetic validation, and independent processing and verification states.

**The system and implementation approach:**

A GCP-hosted portable modular monolith. One Python FastAPI codebase produces two Cloud Run service entry points: a public API (authenticated by Firebase Identity) and a private worker (accessible only through Cloud Tasks OIDC invocation). Image bytes flow directly from the PWA to private Cloud Storage via short-lived signed capabilities, bypassing the API for throughput. A Cloud Scheduler reconciliation sweep detects and recovers receipts stranded in transitional states, compensating for the non-atomicity between PostgreSQL state transitions and queue task creation. The extraction provider sits behind a protocol interface so the AI vendor can be replaced without touching domain or validation code. Money totals are stored as integer minor units (bigint). The domain layer has no dependency on cloud provider SDKs.

**The critical constraints:**

1. An acknowledged receipt must never be lost (REL-001).
2. Only the allowlisted owner can reach private functions or trigger expensive processing.
3. The extraction runtime has no write authority, no tools, and no credentials.
4. Model output must pass schema and deterministic arithmetic validation before promotion to a current revision.
5. Raw evidence, extraction provenance, and validation findings are immutable and retained indefinitely in V1.
6. Processing state and verification state are independent dimensions.
7. The entire flow from camera open to server acknowledgement must complete within ten seconds under documented conditions, excluding asynchronous extraction.
8. Real financial content must never enter source control, CI artifacts, logs, or public portfolio material.

## 9. Verdict rationale

**Verdict:** Approve with conditions

**Rationale:**

The architecture and engineering plan for planning-baseline-2026-08-12-r1 is fundamentally sound. The core decisions are well-reasoned and appropriately scaled for a single-user production system with a defined evolutionary path. Specifically:

The portable modular monolith with hexagonal dependency direction is the smallest adequate design for this product. It delivers durability (PostgreSQL, Cloud Tasks, Cloud Storage) without microservice complexity. The API and worker sharing one codebase but using separate deployment targets is a correct security and execution boundary. No future architecture has been accidentally pulled into day one; the Actual Budget integration, local LLM, bank connectors, and rental capability are all correctly deferred with stable contracts that will not require redesign.

The immutable revision model, append-only state events, fixed-point integer money representation, and independent processing/verification state machines are correct implementations of the financial invariants required by the PRD and blueprint. They support the longitudinal auditing, reprocessing, and provenance claims that are central to the product value proposition.

The idempotency strategy (client submission key, database uniqueness, deterministic queue task keys, worker version lock) is comprehensive. The acknowledged-evidence durability guarantee (REL-001) is protected by the combination of GCS pre-verification, database atomic state transitions, and the reconciliation sweep. The gap between queue creation and database acknowledgement is recognized and mitigated by design, not ignored.

The extraction provider isolation (ReceiptExtractor interface), multi-layer prompt injection defense (structured schema + deterministic validation + needs_review), and non-negotiable contingency ladder (preserve durability before visual polish) reflect mature engineering judgment.

Five medium-severity findings exist. None is blocking for Gate A, because all five are specification gaps that must be closed in Wave 0 preflight or Wave 1 contract freeze — activities that naturally precede code production. Two findings (F-1, HEIC handling; F-5, cold start) require empirical measurement on real infrastructure and the target iPhone before Wave 1 begins. Two findings (F-2, concurrent worker idempotency; F-3, migration mechanism) require specification in Wave 1 frozen contracts. One finding (F-4, manifest hash algorithm) requires a one-sentence canonical definition in Wave 1 contracts.

No finding reveals a design that is unsafe for the approved scope, irreversibly blocks a future capability, creates an unrecoverable data loss mode, or contradicts the accepted product constraints. The plan may proceed to implementation after the conditions below are satisfied.
